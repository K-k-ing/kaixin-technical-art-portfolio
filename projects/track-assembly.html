02 / 制作问题

赛道改一处，
不应该让所有护栏重新摆一遍。

在赛道搭建中，我反复遇到的不是“放不下一个模型”，而是大量资产都需要复制、旋转、对齐。道路形状一改，左右偏移、弯道资产和坡道朝向又要重新处理。

所以我把目标分成两层：先把重复的空间计算交给程序，再把资产选择与局部修正留给美术。

工具的价值是让路径、规则和资产之间保持可调整的关系，支持围绕 Spline 重新生成，而不是一次生成后就无法修改。

自动化

减少重复操作

沿线采样、方向计算、左右偏移与批量实例布置。

控制权

让美术能够覆盖

独立配置直道、弯道与坡道，必要时手动指定区域类型。

迭代

规则跟随路径修改

调整参数与 Spline 后重新生成，检查新的边界与排列结果。

03 / 编辑器工作流

从路径，到可以检查的实例结果。

参考布局进入编辑器后，我将资产搭建拆为五步。每一步只承担明确的职责，方便调参和排查问题。

  1. 01

    选择路径

    使用目标 Spline，设置道路宽度、生成侧和基础偏移。

  2. 02

    采样与分类

    读取位置与切线，分析直道、弯道、坡道及弯道内外侧。

  3. 03

    配置规则

    分区域选择资产、间距、偏移、模型前向轴与校准旋转。

  4. 04

    人工覆盖

    为特殊距离区间指定类型，修正不符合视觉需求的分类。

  5. 05

    生成与迭代

    通过 HISM 组织重复实例，在视口中检查并重新生成。

04 / 面向美术的控制

同一条路径，不必只有一种重复方式。

我把常用调整集中到中文操作面板，让使用者能够从内容浏览器选择资产，再配置规则，不必为了换一个模型进入代码。

路径与排列，先给出整体约束。

Track Width、左右侧和基础 Offset 决定布置范围。自动间距、最小间距、间距倍率与连续边界排列，用来调整资产之间的衔接。

不同模型自身的前向轴、比例和原点并不一致，因此面板保留前向轴、Pitch / Yaw / Roll、高度与缩放校准。

这些设置服务于原型搭建。紧弯、接缝和穿插仍需要在视口中检查，不能只看参数是否有效。

直道、弯道内侧、弯道外侧，分别配置。

不同道路区域可以使用不同 Mesh 列表、间距与 Offset；弯道内外侧不再被简化成固定的左边或右边。

现有面板已经包含单一、分段和随机展示，以及按长度／数量分段、随机种子等选项。我用这些规则控制资产的组合节奏，再通过真实场景检查效果。

自动分类给出建议，特殊区域由我决定。

方向与高度变化提供道路类型的初步判断，但“数学上像弯道”不一定意味着美术希望换用弯道资产。

通过 Zone Override，我可以按起止距离指定区域类型，并单独启用或停用覆盖区间，让视觉意图有明确的入口。

阈值可调、结果可观察、局部可覆盖，是我对这套自动化流程的基本要求。

01 / 局部坐标

位置正确，还需要方向正确。

将 Spline Tangent 作为局部前向方向，再计算横向与 Up。左右偏移和 Mesh 旋转依赖同一个局部坐标系，避免只在世界坐标中摆放。

02 / 区域分类

水平变化看弯道，垂直变化看坡道。

相邻采样切线的变化用于近似道路弯曲，高度和竖直方向补充坡道判断。检测距离与阈值面向美术调节，不追求所有输入下的绝对分类。

03 / 弯道语义

左 / 右，不等于内 / 外。

道路左右侧由行进方向定义；弯道内外侧还取决于转向。将 Turning Direction 与 Placement Side 组合，才能选择正确的资产规则。

04 / 实例组织

批量生成实例数据，而非大量独立 Actor。

相同 Mesh 通过 HISM Component 管理，每个位置由实例 Transform 描述。目标是降低重复资产的场景组织成本；实际帧率与内存收益仍需要专项测量。

为什么这一版使用 Python 界面？

我用 Python + Tkinter + Unreal Slate Bridge 连接参数面板与编辑器逻辑，尝试在不制作正式插件的前提下快速验证工具工作流。这是 Editor-only Python 工具，不是 Blueprint Editor Utility Widget，也不是游戏运行时系统。

06 / 开发挑战与解决方案

让脚本走出固定的演示条件。

我把问题分别放在空间计算、美术控制和工程结构中处理。下面记录关键判断，而不是仅罗列功能。

01

沿线位置对了，资产朝向却不对。

问题仅使用位置或世界旋转，在急弯和控制点附近难以持续跟随道路。

我的决策用切线建立局部前向，再统一计算横向偏移和旋转；模型自身差异通过前向轴与校准参数处理。

检查重点在弯道、控制点附近检查朝向、接缝与穿插。

02

固定间距无法表达直道和弯道的差别。

问题只做沿线采样，同一种资产会一直铺进不同道路区域。

我的决策比较相邻切线的方向变化，将曲率近似转化为可调检测阈值，再选择不同规则。

检查重点缓弯与急弯需要分别观察，避免把“分类通过”等同于“视觉正确”。

03

坡道在俯视图里，可能仍是一条直线。

问题仅分析 XY 方向会遗漏道路的竖直变化。

我的决策补充高度与竖直方向分析，并为坡道保留独立的模型、间距和偏移配置。

检查重点本页主要演示平面闭合赛道；坡道能力有文档和界面依据，但不是这段录屏的重点验证对象。

04

固定左侧不能一直代表弯道内侧。

问题左转和右转会改变某一侧对应的内外语义。

我的决策将道路转向与布置侧组合判断，为弯道内外侧分别设置资产规则。

检查重点在不同转向下复核外侧护栏、内侧装饰的位置关系。

05

程序分类正确，也可能不符合美术意图。

问题某段缓弯可能需要继续使用直道资产，以保持边界节奏。

我的决策加入按距离区间的 Zone 手动覆盖，允许自动建议被明确修正。

收获自动化应该承担重复劳动，而不是剥夺美术对特殊区域的决定权。

06

重复资产越来越多，场景管理越来越重。

问题大量独立 Static Mesh Actor 会增加场景组织、选择与重新生成的管理成本。

我的决策使用 HISM 组织相同 Mesh 的实例，把生成结果转化为批量实例数据。

验证边界这是结构上的选择，不用未经测量的帧率或效率提升比例包装结果。

07

功能增加后，各类规则开始互相影响。

问题分析、分类、布置与 UI 混在同一执行函数中，会让修改难以定位。

我的决策逐步拆分 Analysis、Classification、Placement、Generation 与 UI 的职责。

收获工具的可维护性需要随功能一起设计，而不是等到完成后再整理。

08

核心函数正常，界面操作仍可能出错。

问题默认值、按钮绑定或参数映射错误，也会造成最终生成异常。

我的决策分别使用核心逻辑回归与 UI Bridge 回归，检查规则本身和参数传递链路。

验证边界开发记录包含这两类测试；网页展示不等于对任意 UE 版本、任意资产的兼容性保证。

07 / 我的工作

把制作经验，变成可执行的工具规则。

我负责梳理参考到布局、再到资产搭建的制作流程，将赛道中的重复工作拆解为可调整的空间规则。技术实现围绕 Unreal Editor Python、Spline 几何分析、道路分类、程序化布置和 HISM 生成展开。

同时，我设计面向美术的参数控制和中文操作面板，围绕核心逻辑与 UI 传参进行回归验证，并用实际赛道场景检查排列效果。

  • 参考分析与工具工作流设计
  • Spline 采样与局部坐标计算
  • 道路分类、内外侧与手动覆盖
  • 资产规则、HISM 与重新生成
