01 / Background and Planning Test

Not more geometry.
The geometry the asset needs.

While creating 3D assets with AI, I found that a higher target face count did not always produce a better result. For simple assets defined by flat surfaces, sharp folds, and a clear silhouette, additional geometry can introduce unwanted undulations and unstable surface structure.

I tested a metal five-pointed star. The left image is an approximately 500-face version generated after budget planning; the right uses more than 2,000 faces. In this pair of results, the planned lower-count version has clearer primary facets and a better-preserved silhouette.

Inspect the wireframes and actual counts: 503 / 2,056 faces

This case supports planning around structural needs instead of defaulting to dense output. It does not prove that fewer faces always produce higher quality. These source screenshots report faces; the planner and subsequent validation use triangles. The two units are not treated as interchangeable.

02 / Tool Objectives

Answer three production questions before generating.

Where should I start?

Choose a starting budget

How many triangles should I test first, instead of selecting the highest density by default?

Where does geometry matter?

Separate geometry from texture

Which structures need real geometry, and which details can be represented by textures, normals, or materials?

What is appropriate here?

Account for the use case

Which budget tier should I prioritize for the asset’s usage, viewing distance, and target platform?

The goal is to turn experience-driven parameter selection into a workflow with visible reasoning, adjustable conditions, and results that can be checked.

04 / Implemented Features

Make the structural reasoning
as inspectable as the number.

Reference input and preview

Click or drag to upload, preview the image, validate its dimensions and file size, and reset or retry with visible error feedback.

Live AI structure analysis

A multimodal vision service analyzes silhouette, flat and curved surfaces, thin structures, small details, symmetry, repetition, and occlusion uncertainty, returning GeometryImageAnalysisV1 data.

Three explainable budget tiers

A local TypeScript calculator combines structural features with usage conditions to produce a minimum candidate, a balanced budget, and a high-budget test value.

Visible source and runtime state

The interface shows backend connectivity, Mock / Real AI mode, the model, and the analysis source. A failed live request never silently returns mock data as if it were a real analysis.

Geometry vs Texture

Spatial forms such as the top rings, upturned toes, and bells may need geometric support. Diamond color patterns, shallow seam shadows, and material highlights may instead be represented through textures or normals.

The result explains which details deserve geometry, helping me check whether visual complexity actually calls for more triangles.

07 / Key Technical Decisions

AI interprets the structure.
Rules calculate the budget.

Instead of asking the vision model for an untraceable face-count estimate, I separated interpretation from calculation.

Vision Layer

Reference → Structured analysis

Silhouette, curved surfaces, thin structures, decorative detail, and uncertainty.

→
Rules Layer

Features + Conditions → Budget

Local deterministic calculation with candidate ranges and explanations.

→
Validation Layer

Generated asset → Review and refine

Record actual triangles and inspect geometry, normals, and textures.

The same structured input produces the same calculation, making recommendations traceable and rules easier to adjust. Determinism does not mean accuracy, but it makes accuracy easier to evaluate and improve.

One consistent unit

Use triangles rather than mixing faces, polygons, and vertices. Compare actual exported meshes—not just the target value on a generator’s slider.

Isolated service adapters

Vision services sit behind a dedicated adapter, with mock and live calls kept separate. Provider changes have less impact on the frontend and budget calculator.

Data and credential boundaries

Responses undergo JSON extraction, runtime validation, and normalization before reaching the calculator. API keys are read only by the backend, never returned to the frontend or included in request logs.

08 / Challenges and Solutions

From layered diagnostics
to testable budget decisions.

Replace vague errors with layered diagnosis; separate visual complexity into geometry and texture needs; find a useful budget between low counts and form preservation.

Challenge 1

Analysis failed with only Failed to fetch

Problem

The image preview worked, but clicking Analyze produced no result. The error message did not reveal where the failure occurred.

Cause

Investigation found that a port conflict had stopped the development process, breaking the local request chain.

Solution

  • Resolve the port conflict and standardize the listening address.
  • Correct the frontend/backend proxy target and use relative API paths.
  • Add health checks and status endpoints.
  • Replace the generic error with layer-specific feedback.

TakeawayA reachable frontend, a reachable local backend, and a working remote model are three different states. Each needs its own check and status display.

Challenge 2

Visual detail is not geometry complexity

Problem

Highlights, patterns, shadows, and shallow textures can make an image appear complex. Translating them directly into geometric requirements can inflate the budget.

Solution

Explicitly distinguish:

  • Details that change silhouette or spatial structure.
  • Details that textures, normals, and materials can represent.
  • Structure that a single view cannot establish.

The result presents geometry and texture guidance side by side so users can inspect the AI’s reasoning.

TakeawayGeometry planning is first a structural judgment problem—not a number-prediction problem.

Challenge 3

Keep the count low without losing the form

Problem

Reducing the budget indiscriminately can damage curves, sharp points, and small attachments. Raising it indiscriminately does not guarantee a more accurate result either.

Solution

Provide minimum, balanced, and high-budget tiers. Start with candidate values, then choose progressively through actual generation and inspection.

Include asset usage, viewing distance, and platform conditions so recommendations are not based only on object category.

TakeawayThe goal is not the smallest number. It is controlled geometry cost at an acceptable visual quality.

10 / Value and Next Steps

A reasoned starting point,
not a definitive answer.

Observe generation differences → propose a budget hypothesis → build analysis and rules → apply them in modeling → inspect the result. This process turns face-count selection from open-ended trial and error into a structurally informed starting recommendation.

Record comparable data

Track both target counts and actual triangles, using repeated generation at multiple budgets from the same reference.

Evaluate quality separately

Standardize the view and display conditions. Inspect geometry, normals, and textures separately so a total count cannot hide specific issues.

Keep testing generalization

Test assets not used to tune the rules, building separate budget evidence for different generators and versions.

03 / AI ASSET PIPELINE

AI-Assisted 3D Asset Production Pipeline

From AI concept development and modular asset generation to Blender refinement and Unreal Engine 5 scene validation.

This project explores an AI-assisted workflow for developing game prototype assets across concept design, character and vehicle exploration, modular 3D generation, Blender inspection, asset assembly, material refinement, and Unreal Engine 5 validation.

The goal was not to treat AI-generated models as finished production assets, but to evaluate how AI tools could support early asset development, modular iteration, visual exploration, and real-time scene prototyping.

Pipeline Overview

The workflow separates AI-assisted exploration from manual asset repair and real-time production validation.

Built around a sacred science-fiction civilization, the project covers character concepts, mechanical props, vehicles, drones, architectural ruins, and environmental assets.

The workflow combines concept generation, visual analysis, AI-based 3D generation, modular asset breakdown, Blender inspection and assembly, material refinement, and Unreal Engine 5 scene validation.

03

Asset Decomposition

Complex assets were divided into smaller components to improve generation accuracy, simplify inspection, and support independent replacement and optimization.

Why break the asset apart?

The spacecraft was separated into a main body, ring structure, wings, landing supports, mechanical joints, connectors, and secondary details. Character and robot assets followed the same logic across the head, torso, arms, mechanical frame, armor sections, and functional attachments.

04

Blender Cleanup and Optimization

Parts that became blurred, unstable, or structurally inconsistent during full-model generation were isolated and regenerated separately.

This approach improved local silhouette accuracy, mechanical joint readability, component replacement, detail control, and assembly flexibility.

  1. 01

    Full Generation Review

    Inspect the assembled output and identify unstable regions.

  2. 02

    Isolated Component

    Separate the problematic region from the full generation.

  3. 03

    Refined Component

    Regenerate or replace the part with a more readable version.

  4. 04

    Final Assembly

    Reintegrate the refined component and recheck the complete asset.

06

Findings and Limitations

The workflow remained useful for prototyping, but generated outputs still required close technical and artistic review.

01

Thin Geometry

Thin wings, panels, and mechanical structures may collapse or lose readability during generation.

02

High-Detail Deformation

Increasing model complexity can produce unstable proportions, noisy surfaces, and distorted components.

03

Topology Quality

Generated meshes frequently require manual inspection, cleanup, or replacement before assembly.

04

Component Consistency

Separately generated parts may not share consistent scale, connection points, or visual language.

05

Material Translation

Roughness, reflective surfaces, transparency, and layered wear are not always transferred reliably.

06

Reference Preparation

Clean, isolated, and purpose-built references often perform better than direct crops from complex concept images.

07

Cross-Asset Consistency

Maintaining a unified visual language across characters, vehicles, props, and environments remains difficult.

07

Additional Experiments and Reflection

The final result is a documented prototype workflow, not a claim of fully automated production readiness.

Final Outcome

The project produced a set of character, vehicle, mechanical, and environment prototypes that were assembled and evaluated within Unreal Engine 5.

The project identifies where AI-assisted tools can support concept exploration, modular generation, and early prototyping, while also showing why manual inspection, assembly, material refinement, and real-time validation remain essential.

What I Learned

This project strengthened my understanding of modular asset planning, reference preparation, AI-generation limitations, Blender-based inspection, environment assembly, and Unreal Engine validation.

It also demonstrated that the most reliable workflow was not full automation, but a controlled process in which AI generation, artist judgment, modular design, and real-time testing supported one another.
